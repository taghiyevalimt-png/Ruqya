# DISASTER_RECOVERY — восстановление «Mərkəz» после сбоя

Цели заказчика: **RTO ≤ 4 ч** (время до работающей системы), **RPO ≤ 24 ч** (сколько изменений можно потерять).
Все цифры ниже — из учений с доказательствами в `evidence/stage6/`; что не отрабатывалось на деле, помечено «НЕ ПРОВЕРЕНО».

## 3. Сценарии

### A. Ошибочно удалена или изменена одна запись
1. Вкладка настроек → раздел сотрудников → «Dəyişikliklər jurnalı» (только админ) → найти запись → «Bərpa et». Это вызывает `ruqya_restore`.
2. Если запись изменена, а не удалена: в журнале видны старые значения; внесите их вручную.

### B. Потерян проект Supabase (или нужно перейти в другой)
1. Создать новый проект (тот же регион, PostgreSQL 17). Dashboard → Connect → Session pooler: строка подключения.
2. Скачать последний архив (Actions → Database backup → артефакт, либо копия владельца вне GitHub). Проверить и расшифровать по docs/BACKUP.md.
3. `sh scripts/restore.sh decrypt ruqya-backup-<время>.tar.gpg DIR`, затем `sh scripts/restore.sh target DIR "<строка подключения нового проекта>"`. Скрипт откажется восстанавливать в живой проект (`LIVE_REF`) и в непустую базу, сверит все таблицы.
4. Authentication → Sign In / Providers: выключить регистрацию (sign-ups off), как в живом проекте; Site URL — адрес сайта.
5. Сайт: `SUPABASE_URL=… SUPABASE_ANON_KEY=<publishable key нового проекта> python3 tools/configure.py OUT`, опубликовать `OUT` (GitHub Pages: заменить файлы и `sh publish.sh`, или свой сервер, сценарий C).
6. Поменять адрес в местах из таблицы раздела 4, пересобрать APK, если менялся адрес сайта.
7. Проверка: вход владельцем, видны записи, создать и отменить тестовую запись, `node tests/perf/live-network.js`.

### C. Переезд на серверы заказчика (закрытый контур)
1. База и API: Supabase self-hosted (docker compose из официального репозитория supabase/supabase) или любой PostgreSQL 17 + PostgREST + GoTrue тех же версий. Структура: `db/schema_live_20261116.sql`, затем `sql/2026-11-realtime.sql`, затем миграции из списка `AFTER` в `tests/dbcopy.js`. Данные — по сценарию B, шаг 3.
2. Сайт: `deploy/nginx.conf` + `deploy/merkez-headers.conf` (все заголовки безопасности; проверено на Ubuntu 24.04, evidence/findings/S-01/deploy-check.txt). Сайту не нужен интернет: шрифты и библиотеки лежат в `vendor/`, запросы только к своей базе (evidence/stage0/baseline/live-network.json: страница входа обращается только к своему адресу).
3. Копии: `backup.yml` рассчитан на GitHub Actions. В закрытом контуре те же шаги (dump → шифрование → сверка) запускаются по cron на сервере; команды — в самом файле.

### D. Потерян GitHub (аккаунт или репозиторий)
Код — из любого клона или архива релиза (SHA256SUMS). Копии — из мест вне GitHub (у владельца). Секреты Actions восстановить нельзя (GitHub не показывает их повторно): ключи создаются заново (раздел 5).

### E. Утечка ключа или пароля
Раздел 5: заменить ключ, затем проверить журналы Supabase (Auth, API) за время утечки.

## 4. Что меняется при переезде (B-12)

| Где | Что | Как поменять |
|---|---|---|
| `index.html` (`SB_URL`, `SB_KEY`, CSP `connect-src`) | адрес проекта и публикуемый ключ | `tools/configure.py` (меняет всё сразу и пересчитывает CSP) |
| `android/.../MainActivity.java` (`HOST`) | адрес сайта для APK | поменять, push в `android/**` → новый APK |
| `.github/workflows/keepalive.yml` | адрес проекта и публикуемый ключ (будит бесплатный проект) | поменять оба значения |
| `.github/workflows/audit-probe.yml` | адрес сайта и проекта | поменять |
| `scripts/restore.sh` (`LIVE_REF`) | ссылка на живой проект (защита от восстановления поверх него) | поставить ссылку нового живого проекта |
| секреты Actions `SUPABASE_DB_URL`, `BACKUP_PASSPHRASE` | подключение и пароль копий | Settings → Secrets → Actions |
| `tests/perf/live-network.js`, `tools/secret_scan.js` | адрес для проверки сети; разрешённый публикуемый ключ | поменять |

## 5. Замена ключей и паролей
| Что | Где меняется | После замены |
|---|---|---|
| Публикуемый ключ Supabase | Dashboard → API Keys → создать новый publishable, старый отключить | `tools/configure.py`, publish, keepalive.yml |
| Пароль базы | Dashboard → Database → Reset password | секрет `SUPABASE_DB_URL` |
| `BACKUP_PASSPHRASE` | `openssl rand -base64 32` → секрет | старые архивы открываются старым паролем — хранить оба |
| Ключи DR | `openssl genrsa -out dr_private.pem 4096`, `openssl rsa -in dr_private.pem -pubout -out .github/dr_public.pem` | новый открытый ключ — в репозиторий, закрытый — владельцу |
| Ключ подписи Android | секреты `ANDROID_KEYSTORE_*` | новый ключ требует переустановки APK на телефонах |
Учения по замене живых ключей не проводились: это остановило бы работу центра (НЕ ПРОВЕРЕНО, порядок проверен чтением кода и настроек).
